## 2. 功能详解

- **两层偏好解析全部走 `ResolvePreferredChannelsTx`**（`repo/preferences.go`）：全局层是天花板（没设置过默认是 `[IM]`，不是 proto 里全部三个通道——EMAIL/SMS 本阶段没有适配器，默认打开只会造出死记录）；分类层是天花板的子集（没设置过跟随全局，设置过就与全局取交集，不能靠分类层突破全局关闭）；critical 类别解析出空集时兜底成默认全局值。**这个兜底不覆盖"用户被停用"**——那是 `consumer.workflowTaskCreatedHandler` 在拿到解析结果之后另外判的一层，两层判断故意不合并。
- **`SetPreferences` 是整份替换，不是增量合并**（同 REST PUT 语义）：先删掉这个 `sub` 的全部偏好行，再按请求体重新插入——没提交的分类会恢复"跟随全局"，不会残留上一次的值。critical 类别显式提交空数组会被 `ErrInvalidArgument` 拒绝；没提交（跟随全局）不受这条限制，即使全局本身是空，解析时的兜底会接住。
- **`command_idempotency` 表建过又删掉**（`migrations/003`）：002 迁移照抄 `erp-inventory` 的模板建了这张表，全项目核对后确认它只用于"外部调用方提供 idempotency_key 的写命令 RPC"，而本组件的两个写入路径（`SetPreferences` 天然幂等、`CreateRecord` 事件驱动由 `event_inbox` 去重）都不需要它——SOP-R 三步法（自己先设计→查证→自己纠正）的一次真实应用。
- **`notification_records` 的状态机严格四段**：`PENDING`（建记录，还没发 dispatch）→ `ACCEPTED`（适配器已受理）→ `SENT`/`FAILED_PERMANENT`（终态）；`RETRYING` 是 `ACCEPTED` 之后收到失败结果、等待重试的活跃态。`SUPPRESSED` 是另一条独立的终态路径（被用户偏好/停用挡掉，不经过 PENDING 之后的正常流转）。
- **重试重发的 `Event.Version` 必须递增**（`consumer.go` `publishIMDispatchTx`）：这是本组件实现中真实发现的 bug——`dispatch.im.v1` 的 `aggregate_id` 固定是 `record_id`，`event_inbox` 按 `(subject, aggregate_id)` 只接受版本严格递增的事件。第一版重试重发时沿用了 `Version: 1`，会被适配器的 `event_inbox` 当成重复消息静默吞掉，症状是 `retry_count` 涨了、适配器那边却什么都没收到，且没有任何报错。改成 `Version = attempt`（`attempt = retry_count + 1`），并把 `attempt` 加进 payload 供适配器算自己的结果事件版本。
- **PostgreSQL `text[]` 读出来不能直接 `Scan` 进 `*[]string`**（`repo/pgarray.go`）：pgx/v5 的 `database/sql` 通用接口会报 `unsupported Scan`（真机测过），只能把目标类型定成 `string` 接住原始文本自己解析 `{a,b}` 格式；写入方向不需要对应的 encode，pgx 能直接把 `[]string` 编码成数组参数。
- **月分区/周分区都不需要 `ALTER TABLE ... OWNER TO`**（`backend/internal/partition/`）：真机验证过，`SET LOCAL ROLE` 之后 `CREATE TABLE` 建出来的分区所有者就是当前角色本身；迁移建的初始分区所有者虽然不是 `infra_notification_rw`，但这个 schema 配了 `ALTER DEFAULT PRIVILEGES`，DML 不需要"是不是 owner"。

## 3. 完整契约清单

**gRPC `infra.notification.v1.NotificationService`**：

| rpc | 类型 | 说明 |
|---|---|---|
| `BatchGetRecords` | 读 | 防 N+1 |
| `ListRecords` | 读 | 组件间协议，不做数据权限过滤 |
| `GetPreferences` | 读 | 按 `sub` 查任意用户的偏好 |
| `SetPreferences` | 命令 | 天然幂等，无 `idempotency_key` |

**REST**（`/infra/notification/**`）：

| 路径 | 权限键 | 说明 |
|---|---|---|
| `GET /notifications` | `infra.notification.view` | 我的通知历史 |
| `GET /preferences` | `infra.notification.preference.edit` | 我的通道偏好 |
| `PUT /preferences` | `infra.notification.preference.edit` | 改偏好，critical 类别不能清空 |
| `GET /admin/records` | `infra.notification.admin` | 排障视图 |

**发布事件：** `infra.notification.dispatch.im.v1`/`.dispatch.email.v1`（核心）、`.sent.v1`/`.failed.v1`（旁路）。
**消费事件：** `infra.workflow.task.created.v1`、`infra.iam.user.{created,updated,disabled}.v1`、`integration.im.result.v1`（族级）。

详细字段与判据见 `docs/design/infra-notification.md`。

## 4. 数据模型

| 表 | 分区 | 说明 |
|---|---|---|
| `notification_records` | 月 | 唯一无限增长的表，归档窗口 3 个月 |
| `notification_preferences` | 不分区 | `(sub, category)` 唯一，`category=''` 是全局层 |
| `user_contacts` | 不分区 | iam 事件快照，永不归档 |
| `event_outbox`/`event_inbox` | 周 | 标准两张 |

**实测验证**（真实 Postgres + 真实 NATS，非 mock）：两层偏好解析（含 critical 兜底与"分类不能突破全局"）、`SetPreferences` 整份替换与 critical 空数组拒绝、状态机 `ACCEPTED→SENT`/`RETRYING→FAILED_PERMANENT`、停用用户覆盖 critical 兜底、重试重发的 outbox version 严格递增（`[1, 2]` 而不是 `[1, 1]`）、owner 维列表过滤、迁移连跑两次幂等、Docker 镜像自检。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| 通知一直停在 `ACCEPTED` 不推进 | 适配器的延迟回查没有真的发 `phase=CONFIRMED` 的结果事件——可能是适配器进程本身有问题，或者 `integration.im.result.v1` 的 `record_id`/`adapter` 字段对不上 | 查 `integration-im-dingtalk` 那边的 `delivery_attempts` 表有没有对应记录；确认 `target_adapters` 里确实点了名 |
| 重试了但适配器那边什么都没收到 | 重发的 `dispatch.im.v1` 用了与初次派发相同的 `Event.Version`，被 `event_inbox` 当重复消息吞掉 | 检查 `event_outbox` 里同一个 `record_id` 的多条 `dispatch.im.v1` 记录，`version` 列必须严格递增 |
| `PUT /preferences` 对 `workflow_task` 返回 400 | 请求体给 `category_channels.workflow_task` 传了空数组——critical 类别不接受清空 | 不提交这个字段（跟随全局）或至少保留一个通道 |
| `notification_records` 建分区失败，报"分区范围不许重叠" | 迁移里手写的初始分区名与后台任务的命名格式不一致 | 核对 `migrations/001` 与 `backend/internal/partition/monthly.go` 的 `monthPartitionName` 是不是同一套 `表名_YYYY_MM_01` 格式 |
