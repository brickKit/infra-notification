# infra/notification 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、规则、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。

跨组件的规则在装配项目：通知在协议 10，后台工作在协议 01，投影在协议 02，提醒以通知意图发出在协议 09，会话类记录的通知在安全 05、08；决定 D68（只经事件读员工）、A83。发送方怎样发出意图、本组件怎样认收在线协议第 18 章（通知意图）。首批范围是装配项目阶段计划 C8 的 P0 定的（第一个发送方是流程内核，维护者定；其余 AI 定，待复核）。

## 边界

通知：收下各发送方发出的通知意图，按类别与收件人的偏好决定投到哪些渠道，把岗位展开为当时的持有人；渠道是本组件自己的站内消息与部署配置的外部渠道成员（线协议第 20 章；第一个是 `integration/im-dingtalk`）。

| 不在这里 | 归谁 |
| --- | --- |
| 什么时候该通知谁 | 发送方（业务组件、流程管理方、安全组件）发出意图 |
| 链接打开后能看到什么 | 链接指向的组件按收件人当时的权限检查：通知不授予权限 |
| IM、邮件、短信的投递与渠道账号 | 渠道成员（`integration/im-*` 等）：本组件经它的共享系统面 `be.channel.v1.ChannelService` 交出投递 |
| 审批的决定、交互按钮的动作 | 所属组件签发与核对动作令牌（线协议 P17.19、P20.7），渠道成员收回调；本组件只把令牌转交给渠道成员 |
| 营销同意 | `mdm/partner` 的联系人属性（A83） |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 通知意图 | 发送方要通知某些人一件事：类别、收件人、门铃式的内容、到期、合并键（线协议第 18 章） | `intent`；事件 `<领域>.<组件名>_notification.intent.v1`，载荷 `be.notification.intent.v1` |
| 发送方 | 部署配置列出的、本组件订阅其意图的组件 | 配置键 `NOTIFICATION_INTENT_SOURCES`（NT01） |
| 类别 | 封闭的目录（线协议 P18.3）；决定能否退订与默认渠道 | `category` |
| 收件人 | 主体（账号），或岗位（投递时展开为当时的持有人） | `recipient` |
| 渠道 | 投递的方式：站内消息，或部署配置的外部渠道（渠道名 = 渠道成员） | `channel`：`in_app`、`dingtalk`… |
| 偏好 | 一个人对“类别 × 渠道”的开关 | `preference` |
| 站内消息 | 写给一个主体的一条消息：标题、链接、已读、已撤回 | `message` |
| 投递 | 一个意图对一个收件人在一个渠道上的结果：已写入（站内）、已交出（外部渠道受理）、没有渠道账号、按偏好不投、过期丢弃、无法展开 | `delivery` |
| 合并键与合并序号 | 同一发送方、同一合并键的意图里，序号大的取代序号小的（例：一个任务的待审批消息，序号是任务的版本） | `collapse_key`、`collapse_seq` |
| 撤回意图 | 只有合并键与序号、没有收件人与内容的意图：只做取代（例：任务已决定） | — |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `intent` | 发送方、意图身份、类别、收件人、标题、链接、模板与参数、合并键与序号、动作授权的身份与接受动作的渠道（NT14；不是秘密）、到期、发生与收到的时刻、状态（`pending` 等投递、`done` 每个收件人都有了结果、`superseded` 被取代或迟到作废） | `done`、`superseded` 保留 90 天后删（只用于去重与排障） |
| `collapse` | 发送方 × 合并键 → 见过的最大序号（NT04） | 保留 400 天（长于任何意图与消息） |
| `message` | 站内消息：主体、意图（发送方 + 意图身份）、类别、标题、链接、模板与参数、发送方与合并键（撤回按它找，不经意图）、创建时刻、已读时刻、撤回时刻 | 保留 180 天后删（以后按协议 11 转层） |
| `preference` | 主体 × 类别 × 渠道 → 开或关；没有行就是类别的默认 | 随主体 |
| `delivery` | 意图 × 收件人 × 渠道 → 结果与时刻，唯一。收件人是主体：`written` 已写入、`preference_off` 按偏好不投、`expired` 过期丢弃；外部渠道另有 `pending`（带投递身份与下次尝试的时刻，等调用渠道成员）、`handed_over` 已交出、`unmapped` 没有渠道账号、`failed`、`superseded`（意图被取代）；收件人是岗位（`position:<法人>/<岗位>@<日期>`）：`expanded` 已展开（持有人各有自己的一行，岗位不再展开）、`unresolvable` 展开不了、`expired` 到期时投影仍不完整 | 随意图 |
| `rejected_intent` | 被拒的意图：发送方、意图身份（读得出时）、原因、时刻（另写安全审计） | 保留 90 天 |

员工投影（任职与账号关联）是 SDK 的投影（`be.flow.employee`，水位来源 `mdm/employee`），本组件只读它展开岗位。

## 规则

| 规则 | 内容 |
| --- | --- |
| NT01 | **发送方与订阅**：`NOTIFICATION_INTENT_SOURCES` 是逗号分隔的发送方组件 ID（例 `erp/purchase,erp/payment`）；格式不对或重复，成员启动失败。每个发送方的流与意图的事件类型由组件身份推出（线协议 P18.2：`erp/purchase` 的流 `erp.purchase`，类型 `erp.purchase_notification.intent.v1`），启动时各订阅一次；没有配置时不订阅 |
| NT02 | **认收**（P18.8）：发送方以**意图所在的流**为准——消息系统按服务身份限制谁能在哪个流上发布，而信封的来源与载荷里的发送方都是发布方自己写的。按这个顺序核对，第一个不满足的拒收：载荷不是 JSON 或不合 `be.notification.intent.v1`（`malformed`，类别另算）；载荷里的发送方或信封的来源不是这个流的属主（`not_the_sender`：列在配置里的发送方冒充别人）；类别不在目录里（`unknown_category`）；投递意图的到期不晚于发生（`malformed`）。拒收记 `rejected_intent` 与一条安全审计、不投递；同一意图重投时不重复记。以“发送方 + 意图身份”去重，同一意图再到不再处理（P18.9）。没列在配置里的组件本组件根本不订阅（NT01），它发的意图到不了这里 |
| NT03 | **类别目录**：`approval_task`（可关，默认开）、`due_reminder`（可关，默认开）、`security_alert`、`legal_notice`（必须送达：偏好关不掉）、`external_comm`（可关，默认开）、`marketing`（可关，默认关）；默认渠道：站内一定在内；`approval_task`、`due_reminder`、`security_alert` 另加全部配置的外部渠道（线协议 P20.3） |
| NT04 | **合并与撤回**（P18.7）：收下带合并键的意图时，在同一个事务里锁住 `collapse` 的“发送方 + 合并键”一行：序号不大于记下的，这个意图直接 `superseded`（迟到的旧意图，不投递）；更大的，记下新序号，同一发送方、同一合并键的 `pending` 意图转 `superseded`，站内消息（按消息上的发送方与合并键找）记撤回时刻（不删）；撤回意图做完这一步直接 `done`。结果不依赖到达顺序与并发取代时在同一个事务里，被取代的意图还 `pending` 的外部投递记 `superseded`（不再调用渠道成员） |
| NT05 | **投递**：后台工作逐个认领 `pending` 的意图，每个一个事务（原子认领，协议 01；一个出错不连累别的，也不长时间压着行锁）：把岗位展开为持有人（NT06），对每个主体按类别与偏好（NT07）在每个渠道投递（站内渠道就是写一条站内消息），每次投递在 `delivery` 里唯一，已有结果的跳过（重试不重复写）。同一主体经几个收件人（本人与他持有的岗位）到达时只有一行、只投一次。所有收件人都有了结果（主体有投递结果，岗位展开了或记了无法展开）：意图 `done`，发投递结果事件（NT10）。还有岗位在等投影：留在 `pending`，下一轮再来。**到期**：到期已过时，还没结果的主体与还在等的岗位记 `expired`，意图 `done`。**投递的轮次**：收下一个投递意图时在同一个事务里排一轮（`deliver-now`；已经排着一轮时不再排），员工投影变化而有意图在等时也排一轮，此外每分钟一轮兜底；所以等投影的岗位与已到期的意图最迟在一分钟内收尾。一轮里每个意图只试一次，等投影的不挡后面的 |
| NT06 | **岗位展开**（P18.4）：按员工投影，在收件人给出的日期（没给时是投递当天的协调世界时日期）有效任职的员工的有效账号。投影不完整时不按旧数据展开，等下一轮（到期见 NT05）；展开出空集记 `unresolvable`。**只展开一次**：展开成功记 `expanded`，同一意图之后的轮次不再展开它（意图还在等别的岗位时，岗位换了人，新的持有人不会再收到，前一任已收到的也不会被改记成过期）。部署没有 `mdm/employee`（可选依赖缺席：没有注入它的地址，同 SDK 流程内核判断员工目录的方式）时，岗位类收件人立刻记 `unresolvable`，不等 |
| NT07 | **偏好**（按“类别 × 渠道”）：可关的类别，收件人关了某渠道就不在那个渠道投，记“按偏好不投”；必须送达的类别只有站内关不掉：站内不看偏好，**到期也照写站内消息**（协议 10：必须送达的类别转站内；P18.6）；外部渠道看偏好、照常投一次，不为“必须送达”重试或到期转（线协议 P20.4） |
| NT08 | **我的站内消息**：只列调用者自己的消息（数据范围是“收件人是我”），新的在前，游标分页；可只列未读；答复带未读数。已撤回的照常列出、标明已撤回，不算未读。标为已读只对自己的消息，别人的答 404；全部标为已读只改自己的 |
| NT09 | **我的偏好**：读取答目录里每个类别 × 渠道（站内与配置的外部渠道）的开关（没有行的取默认）与能不能改；修改按“类别 × 渠道”判断：必须送达的类别的站内答 `REQUEST_INVALID`，其余都能改；不认识的渠道答 `REQUEST_INVALID` |
| NT10 | **投递结果事件**：每个投递意图成为 `done`（NT05）且外部投递都有了结果（NT13）时，在本组件的流上发 `infra.notification_delivery.recorded.v1`（增量事实）：发送方、意图身份、类别、每个收件人在每个渠道的结果；不带标题与链接 |
| NT11 | **清理**：每天删过了保留期的意图、站内消息、合并键的记录与被拒的意图 |
| NT12 | **过期的计数与告警**：每个过期丢弃的投递按类别与渠道计数（指标）；必须送达的类别有岗位到期时仍展不开（记 `expired`）或 `unresolvable`，写一条告警级日志（主体不会过期：照写站内）；外部渠道持续不可达超过 1 小时，写一条告警级日志（`event=notification_channel_unreachable`） |
| NT13 | **外部渠道**（线协议 P20.1、P20.3）：`NOTIFICATION_CHANNELS` 是逗号分隔的“渠道名=组件身份”（例 `dingtalk=integration/im-dingtalk`）；格式不对、重名、渠道名是 `in_app`、配置的组件不在清单的可选依赖里，成员启动失败（每加一个渠道成员，清单补一行可选依赖）。NT05 的一轮对外部渠道只写投递行 `pending`（带投递身份 UUIDv7、下次尝试的时刻），不调用外部；`pending` 不是结果，下一轮不跳过它，也不重写它。**外部投递的作业**（`deliver-external`，每 15 秒与收下意图时排一轮）按行认领到期的 `pending`（`FOR UPDATE SKIP LOCKED`，一轮至多 200 行），在事务之外调用渠道成员的 `Deliver`（不在事务里发网络调用），按答复在新事务里记结果：`accepted` → `handed_over`，`unmapped` → `unmapped`；可重试（不可达、超时、`DEFINITION_PENDING`、视图未就绪、`UNAVAILABLE`）→ 留 `pending`，按协议 10 退避（1 分钟起、翻倍、单次上限 1 小时）；不可重试（`REQUEST_INVALID`、`IDEMPOTENCY_KEY_REUSED`、`PERMISSION_DENIED`、其余）→ `failed` 并告警。同一渠道在一轮里不可达一次，这一轮跳过它其余的行。意图到期时还 `pending` 的记 `expired`。意图的状态只看站内与展开：外部投递还 `pending` 的意图也可以 `done`；`done` 的事件（NT10）在外部投递都有了结果之后再发 |
| NT14 | **动作**（线协议 P18.11、P20.5）：意图的 `actions`（动作授权的身份，不是秘密）与 `action_channels` 随意图存；调用 `Deliver` 时，只对 `action_channels` 里的渠道成员、按投递的主体取它那一个动作；站内消息不带动作 |

## 事件

发布：`infra.notification_delivery.recorded.v1`（NT10）。订阅：部署配置列出的发送方的 `<领域>.<组件名>_notification.intent.v1`（订阅随配置在启动时建，NT01）；`mdm.employee`（经 SDK 的员工投影，部署有 `mdm/employee` 时）。`component.yaml` 的 `events.subscribes` 写不出“任何组件的 `_notification.intent.v1`”（同统一待办）：首批列出两个已知发送方的前缀（`erp.purchase_notification.*`、`erp.payment_notification.*`），新的发送方上线时只为 BrickKit 的依赖显示补一行，运行不受影响。

## 部署与替换

低负载，后台为主，适合外壳（`be/go-infra`）。同契约的通知实现可替换；渠道成员多选并存。

## 验证故事

1. 审批任务分配给岗位的持有人：持有人的站内消息里出现待审批的消息，链接指向待办；任务决定后，这条消息标为已撤回。
2. 收件人已离岗时，按当时的持有人投递（岗位类收件人投递时展开）。
3. 关掉“审批待办”之后不再收到这一类的站内消息；“安全提醒”关不掉。
4. 列在配置里的发送方冒充别的组件发出的意图不投递，留下被拒的记录与安全审计；没列在配置里的组件发的意图根本不被订阅。
5. 新的发送方上线：按共享意图契约发到自己的流，部署配置列出它；本组件的运行不需要改动（清单只为依赖显示补一行）。
6. 任务决定的撤回意图因重投先于原意图到达：原意图到达时已是旧序号，直接作废，不会写出撤不回的消息。
7. 部署配置了钉钉渠道：审批待办同时写站内消息并交给钉钉渠道成员；收件人在钉钉没有账号时记“没有渠道账号”，站内照写；渠道成员暂时不可达时下一轮用同一个投递身份重试，不重复投递。

## 未决问题

- 免打扰时段、摘要合并、每个收件人的速率上限：C10 只有一个渠道、一个发送方，量小，仍没做（线协议第 20 章的“不在本版”）。
- 撤回已投到外部渠道的消息（任务决定后把卡片改成“已处理”）：撤回只影响站内，外部卡片不更新（第 20 章的“不在本版”）。
- 渠道成员的投递结果事实（`sent`、`failed`）本组件不订阅：投递记录停在 `handed_over`。
- 收件人的语言与模板的重新渲染：首批只存模板与参数、原样答回，客户端可以按它渲染。
- 审批待办的到期：任务没有截止时是发生加 24 小时（协议 10 的参数）；本组件积压超过它时，这条消息不再写，任务在待办里照常看得到。
- 审批消息的链接 `/workflow/tasks/{任务身份}` 指向统一待办的前端页面；部署没有统一待办时链接打不开（前端路径随协议 20 的前端设计）。
